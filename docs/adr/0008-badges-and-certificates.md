# ADR 0008: Local badge and certificate service integration

Implemented on `Badges-and-Certificates`, October 15, 2026, at the project owner's request; the owner explicitly approved committing and pushing this reviewed integration to that branch.

Use this repository's Next.js/Material UI portal as the CU Portal. Keep the existing Badging Pilot as a separate loopback service in `badge-service/`, with its SQLite award store, issuer signing identity and frozen certificate snapshots. The pilot's tested editors run in same-origin titled documents inside the native staff workspace; a reproducible asset adapter matches the portal surfaces and light/dark theme. This preserves the editors rather than claiming a complete React rewrite. WordPress bridge source remains an optional legacy adapter and is not the portal runtime.

The web backend checks the current portal staff session and `badges:manage` scope on every staff request, in both mock and configured Canvas authentication modes. Course managers and staff administrators receive that scope in code; other roles cannot use credential tools. The service receives its private award token and a server-derived `portal:<staff-uuid>` actor. Neither browser-supplied roles nor the pilot's local issuer key authorize portal calls. Routes are explicitly allowlisted, mutations require same-origin JSON requests, and private responses cannot be cached.

Learner access uses the portal's existing session and active-account checks, then an explicit operator-approved mapping of portal UUID to badge learner ID in an ignored, private JSON file. Missing links fail closed; there is no email matching, learner picker, query-string impersonation or access to another learner's PDF. Public verification displays only shared credentials and excludes learner IDs and certificate names/PDFs. The optional subsystem is disabled by default.

This extends the local prototype in ADR 0001 and the scope model in ADR 0004. It does not change ADR 0007's TypeScript Canvas course connector: that connector does not acquire a Python dependency. Only certificate generation requires the optional pinned Python renderer. No production Canvas enrollment, completion schedule, real identity migration, production hosting, or Open Badges certification is introduced. Existing Canvas mappings continue to require the pilot's approved configuration and fresh service-side evidence; no portal offering mapping is silently treated as an earning rule.

Private data, issuer keys, access tokens, historical learner records, generated PDFs, and runtime environments are excluded from Git. Connecting an existing pilot requires an operator-reviewed private runtime migration with backups; copying the source does not migrate awards. See [setup, routes and validation](../badges-and-certificates.md).
