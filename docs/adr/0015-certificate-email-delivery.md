# ADR 0015: Certificate email delivery

Accepted October 28, 2026 at the project owner's request.

The integrated credential service owns certificate email previews, a durable PostgreSQL outbox, append-only delivery events, and an optional worker in the existing API process. This worker concerns email only; ADR 0008's request-driven simulated payment workflows remain unchanged. No separate service is started. Sending is explicitly disabled until a provider and its credentials are configured. The requested sender is `continuinged@cedarville.edu`; this address alone is not authorization from an email provider. The initial optional transport adapter implements Resend's HTTPS send endpoint with one recipient per request and a stable provider idempotency key per delivery. No provider account or credentials have been provisioned.

Recipients are resolved from active portal learners through the existing private badge account link. Names, browser-supplied addresses and matching emails cannot establish that link. Missing, inactive or ambiguous links and absent/invalid portal email addresses block delivery. Cohorts filter existing issued certificates through active progress-cohort membership; selecting members does not verify completion, issue credentials or infer an offering-to-badge association. Staff select the certificates to send.

Staff holding `badges:manage` review personalized recipient, sender, subject, message and the original frozen certificate PDF. Previews expire after 30 minutes and belong to the authenticated staff actor. Confirmation queues that exact immutable content; repeated confirmation returns the same jobs. The service rechecks active awards, recipient bindings and configuration when confirming and before sending. The existing renderer verifies the original certificate signature. Confirmation is transactional across the selected certificates; provider outcomes are recorded separately for each recipient.

Any previous queued, sending, accepted, failed or uncertain delivery of the same certificate to the same address blocks a normal send, regardless of format/content changes. Resends require an individually reviewed preview, the latest prior delivery ID and a recorded reason. Pending sends cannot be resent. The database serializes claims across API instances; no provider network call occurs inside an issuance or claim transaction. A sending claim interrupted for two minutes becomes uncertain. Timeouts, ambiguous provider responses and server failures are never automatically retried, including after a restart; staff must inspect the provider and explicitly authorize a resend. Resend's provider idempotency window is an additional defense, not the application's durable duplicate boundary.

Automatic emailing defaults off, uses explicitly saved templates, applies only when a new certificate snapshot is inserted, and writes outbox intent in that same transaction. It never scans old awards or retroactively emails earlier certificates. Disabling the setting cancels queued automatic work before its next send; already-started provider requests cannot be recalled. Missing contacts and fictional demonstration certificates are recorded as blocked. Delivery history distinguishes queued, sending, provider accepted, definite failure, uncertain outcome, blocked and cancelled; acceptance is not proof of inbox delivery. Webhook-based delivery/bounce tracking is outside this addition.

Download links are private bearer capabilities for one certificate and expire seven days after preview creation. Tokens are HMAC-bound to workspace and delivery ID using a separate private persistent key; they are reconstructed rather than stored in the database. Links use the configured public HTTPS origin and carry the token only in the URL fragment. The public download page removes that fragment from browser history and exchanges it in a same-origin POST body, keeping it out of normal HTTP URLs/referrers. Each download rechecks expiry, award validity, signature and active contact binding. Anyone holding a valid link can use it; this is not recipient-authenticated access. Attachments already received cannot be recalled.

Migration `026_certificate_email` adds three workspace-scoped tables and immutable-content/history triggers. The private `certificate-email-link-key` file must be preserved alongside issuer keys, account links and the PostgreSQL backup. Losing it invalidates outstanding links. Existing signed badge/certificate snapshots are not changed.
