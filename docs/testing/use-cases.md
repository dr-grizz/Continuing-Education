# Continuing Education portal systematic test cases

Updated October 21, 2026. Use this guide to test the implemented portal consistently, record reproducible failures, and decide which workflows need another check after a change. It covers the learner, staff, Canvas course connector and Stripe sandbox experiences, including failures, permissions, accessibility and recovery.

This is a test specification, not a completed test report. Start a new [test run record](test-run-template.md) for each run. Existing automated passes and historical demonstrations do not populate the results of a new run.

## Current behavior and scope

- Learner login supports existing CU accounts through Canvas OAuth or explicit local mock mode; see [learner login](../canvas-learner-auth.md). In mock mode, a normalized email selects a demo learner without ownership verification.
- Staff login supports either mock staff selection or configured Canvas OAuth. Canvas verifies the linked staff identity; portal roles authorize portal actions. Canvas permissions and developer-key scopes separately limit course reads.
- Canvas discovery is read-only. Opening or refreshing a preview creates no offerings. Explicit selected-course import creates unpublished drafts with stable mappings; subsequent source refreshes preserve all staff-owned offering fields.
- Canvas course images are the default for imports, with a CU CE fallback. Uploaded portal images and explicit CU CE choices take precedence and survive source refreshes. Only an explicit reset follows the Canvas image again.
- Payments are simulated unless Stripe test credentials are configured. Stripe webhooks or server-side reconciliation confirm payment; a browser success URL does not.
- The demo runs only web and API. Normal simulated fulfillment completes during payment. Delayed/failure simulations and elapsed deadlines advance on authenticated API requests. No work continues while the application is idle; health checks do not advance work. Scheduled Canvas previews are deferred.
- Canvas account creation, real learner enrollment, grades/progress and hosted deployment are future work. See [future cases](#future-integration-cases).

[ADR 0008](../adr/0008-request-driven-demo.md) defines the current processing model. Older dated verification notes that describe a worker or active schedules are historical.

## How to run a test cycle

1. Record the commit, environment, browser, time zone, authentication/payment modes, migration status and tester in the run record. Record the exact offering, registration and approved Canvas IDs used.
2. Prepare the fixtures below in a dedicated test environment. Run manual portal cases first, then the configured Canvas/Stripe cases, and use automated cases for time manipulation, concurrency and hostile provider responses.
3. Execute the smoke sequence before a demonstration or after a restart. Run the broader affected groups before merging or releasing a change.
4. For each case, record the actual result and evidence. A case passes only when all its expected results hold. A missing prerequisite is **Blocked**, not Pass.
5. Repeat failures after a fix and retain both attempts. Restore simulation settings, test records and environment configuration when finished.

### Priority and execution mode

| Value | Meaning                                                                                                                                 |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------- |
| P0    | Core access, payment, data protection or the main learner/staff path. Required for the applicable smoke/release gate.                   |
| P1    | Functional regression and recovery. Run when the affected area changes and before a pilot.                                              |
| P2    | Additional presentation or operational checks. Record any deferred coverage.                                                            |
| B     | Manual browser test using synthetic portal users. No real Canvas or Stripe connection required.                                         |
| C     | Browser test with a configured Canvas OAuth connection and approved staff/course fixtures. Canvas reads only.                           |
| S     | Browser test with Stripe test mode and a functioning test webhook listener.                                                             |
| A     | Automated API/provider test in a disposable database. Use for deterministic failures, clocks, concurrency and authorization boundaries. |
| D     | Operational test in an isolated database or disposable application instance.                                                            |

Use **Pass**, **Fail**, **Blocked**, **Not run** or **Not applicable**. A Not applicable result needs a reason and must not hide a required integration check. Future integration cases are **Deferred** until their feature exists. If repeating a case in multiple browsers or environments, give each execution its own result row.

### Smoke sequence

For the local demo, run `AUTH-01`, `AUTH-02`, `BROWSE-01`, `OFF-01`, `OFF-02`, `REG-01`, `REG-03`, `PAY-01`, `IMAGE-01` and `ACCESS-01`. Add `CANVAS-01`, `CANVAS-04` and `CANVAS-05` when demonstrating the course connector; add `PAY-02` and `PAY-03` when demonstrating Stripe. Use the appropriate permitted staff account for each step.

A smoke pass does not complete concurrency, recovery, live MFA or screen-reader testing.

## Environment and fixtures

### Local setup

Follow the [README](../../README.md#run-locally) for installation and database migration. Preserve existing data and back up before applying migrations. The image controls require migration `020_offering_images` in addition to the earlier migrations.

Use one public origin throughout the browser workflow:

```dotenv
WEB_URL=http://localhost:3050
CANVAS_STAFF_REDIRECT_URI=http://localhost:3050/api/auth/canvas/callback
```

Set `WEB_URL` in the local environment used by the API and website, then restart the application. Open `http://localhost:3050`. The API's internal `API_URL` may remain `http://127.0.0.1:3051`. Cookies for `localhost` and `127.0.0.1` are separate; mixing them invalidates the session-continuity test. Existing Stripe Checkout sessions retain the return URL from when they were created, so create a new session after changing `WEB_URL`.

- **Browser-only track:** use `STAFF_AUTH_MODE=mock`, no Stripe secret key, and a disposable/synthetic database. Restart after environment changes.
- **Canvas track:** use `STAFF_AUTH_MODE=canvas`, the configured developer key/callback, approved linked staff and the course-read scopes in [Canvas setup](../canvas-courses.md). Record the selected subaccount and nested-account setting. A mock staff selection does not provide Canvas API authorization.
- **Stripe track:** follow the [listener instructions](../../README.md#stripe-sandbox-optional), using the same Stripe sandbox as the app. Save the listener signing secret directly in the ignored environment file and restart the API if it changes. Use the application's Test Payment Info for test card details.
- Keep secrets, cookies, OAuth codes, authorization headers and payment credentials out of screenshots, run records and source control.

Use separate browser profiles or private contexts for learner A, learner B and staff. Staff sign-in and learner sign-in are separate sessions; one does not authenticate the other.

### Role fixtures

Use one-role fixtures to test denials. The seeded `admin@cuce.test` account has multiple roles and is useful for setup, but cannot prove a restricted role is correctly denied. In Canvas mode, use approved linked equivalents; do not expect the mock selector to work.

| Content editor           | `content@cuce.test`                                | Sales-page content/media and Explore picks. No offering terms, display-image overrides or course publication.                                                                                                       |
| Support                  | `support@cuce.test`                                | Exception recovery, simulation settings, learner activation, transactions, refund requests and manual Stripe checks.                                                                                                |
| IT/Canvas administrator  | `canvas@cuce.test`                                 | Exception recovery, simulation settings and Canvas read/import/connection management. No offering term edits from this role alone.                                                                                  |

### Offering and content fixtures

Prefix created titles with a unique run label, for example `CE TEST 20261015 01`. Record generated IDs instead of relying on a global course count or a fixed sample enrollment state.

| Fixture   | Required setup                                                                                                                                                                                               |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| OPEN      | Published Self-paced offering, Online, price $1.00, two seats, no approval.                                                                                                                                  |
| LAST      | Separate published Self-paced offering with exactly one seat and no active registration.                                                                                                                     |
| GATED     | Published offering requiring approval; record approval validity.                                                                                                                                             |
| SCHEDULED | Published Scheduled offering with future start/end dates; record enrollment-close days.                                                                                                                      |
| CLOSED    | Scheduled offering with a passed enrollment cutoff, created only in an isolated fixture environment.                                                                                                         |
| UNLIMITED | Published offering with Unlimited seats explicitly selected.                                                                                                                                                 |
| DRAFT     | Unpublished manual offering.                                                                                                                                                                                 |
| IMPORT    | An approved Canvas course with no existing mapping, or a known imported draft when testing refresh only.                                                                                                     |
| IMAGES    | A valid PNG/JPEG/WebP/GIF under 5 MB, a file over 5 MB, an SVG and a non-image renamed as PNG. Use 5 MB as 5 × 1,024 × 1,024 bytes for boundary checks. Use provider mocks for missing/broken Canvas images. |
| CONTENT   | Draft collection, pathway and offering sales page using synthetic text/media.                                                                                                                                |

Use a fresh offering copy for each independent purchase/refund scenario, or record an explicit dependency on a prior case. For example, REG-01's reservation can feed PAY-01; an already enrolled learner cannot start another purchase of the same offering until the implemented refund/re-registration path permits it. Do not treat capacity exhausted by an earlier test as a new application failure.

For live Canvas checks, record the exact approved course IDs and reuse existing mappings where appropriate. Begin with a small reviewed set, at most three courses for this test cycle; do not import the entire subaccount merely to exercise selection. Use mocked-provider tests for changed source dates/publication, hostile URLs, revocation and conflicts rather than modifying live Canvas courses.

## Security testing

Run the [dedicated security test cases](security-test-cases.md) alongside the affected functional groups. They add 24 checks for authentication/permissions, OAuth sessions and grants, CSRF and redirects, Canvas network destinations, payment integrity, content/uploads, disclosure, resource bounds and dependency/configuration review. Six additional security gates cover future real learner login and hosted hardening.

The current demo learner identity is not verified authentication: email selection and the learner UUID cookie can select a known demo identity. Normal ownership/isolation tests do not fix this. Record that known gap explicitly, keep it separate from Canvas staff OAuth results, and do not infer security readiness from a functional or accessibility pass.

Security checks and deferred gates have separate rows in the [shared run record](test-run-template.md#security-case-results). These are specifications, not newly executed tests.

## Evidence and completion

Use the [run record](test-run-template.md) and keep execution evidence separate from expected results. For a failure, capture the case ID, exact setup/IDs, reproducible steps, expected/actual result, timestamp, browser, sanitized screenshot/log and severity. Link an existing issue if appropriate; creating a new issue is a separate requested action.

A current-feature run is ready for review when all applicable P0 cases pass, affected P1 groups are completed or explicitly accepted with reasons, and blocked/live/manual accessibility coverage is visible. Never count Deferred/Not applicable as passed. For a pilot, live integration cases and the manual screen-reader gate need their own evidence; a mocked provider or successful build does not complete them.

After a run, restore Normal simulation and original Explore picks, unpublish test offerings, and sign out of test identities. Remove reserved-domain synthetic learners only through the documented `db:remove-test-learner` workflow when their evidence no longer needs to remain. Do not delete live mappings, staff, payments or shared data as cleanup. Retain backup/evidence references and note any remaining test fixtures.
