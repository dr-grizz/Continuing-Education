# Continuing Education portal security test cases

Updated October 15, 2026. Test authentication, authorization, sessions, integration trust, payments, uploads and sensitive-data handling alongside the [functional cases](use-cases.md). Record results in the [shared test run record](test-run-template.md). These are test specifications; no new security audit or penetration test is recorded by creating this document.

The structure follows the identity, authorization, session, input and business-logic areas in [OWASP WSTG 4.2](https://wstg.owasp.org/v4.2/4-Web_Application_Security_Testing/). Use [OWASP ASVS 5.0.0](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/OWASP_Application_Security_Verification_Standard_5.0.0_en.pdf) when defining verification requirements for a hosted release. This guide is a project-specific subset, not full WSTG/ASVS coverage or certification.

## Scope and current limitations

- **Learner mock mode has a known authentication gap.** `LEARNER_AUTH_MODE=canvas` instead uses verified Canvas origin/user ID and hashed revocable sessions; selectors and email mock login must be rejected in that mode. The isolated learner-auth suite tests these boundaries, but live OAuth and hosted acceptance require separate evidence. The following impersonation limitation applies to mock mode: The demo accepts an email without ownership verification and stores the learner UUID in an HTTP-only cookie. API object-ownership checks operate on that selected identity; they do not make the identity trustworthy. Signing in as another test email or substituting another known test learner UUID can impersonate that demo learner. Do not mark real learner authentication as passed because ordinary A/B isolation tests pass.
- **Mock staff mode is a local test facility.** Anyone who can reach it can select a mock staff identity. Canvas mode must reject that bypass; the two modes need separate results.
- **Canvas OAuth staff sessions have a different boundary.** Staff identity is a verified linked Canvas subject; current portal roles decide actions. The server keeps broker credentials and encrypted Canvas grants. Institution-managed MFA is a separate live assurance check.
- **Uploaded marketing images are public by design**, including draft images at their random media URL. An unguessable UUID is not authorization. Do not use this store for learner documents, grades or other private files.
- **The API's production-mode refusal is a guard, not network access control.** Loopback binding protects the normal local setup; LAN mode changes exposure. Hosted network isolation, real learner authentication, abuse controls and security headers need their own implementation and verification.

Record these design limitations in the run's findings even when expected demo behavior is confirmed. Do not count a successfully reproduced weakness as a passed production security control.

## Test setup and evidence

Use the role, learner and offering fixtures from the [main guide](use-cases.md#environment-and-fixtures), with disposable databases and mocked external services for adversarial cases. Execution modes are A for automated controlled tests, B for browser checks and D for an isolated operational review. All case results start as Not run.

- Limit active testing to the dedicated local/disposable portal instance and synthetic users. Use provider mocks for malicious Canvas URLs, token tampering, signed payment fixtures, replay and time manipulation; no active scanning of Canvas, institutional SSO/MFA or Stripe infrastructure is part of this plan.
- Use two learner identities and one-role staff fixtures, not only the combined-role demo administrator. Test direct API calls as well as hidden/disabled UI controls.
- Use harmless text markers for injection tests. No destructive SQL, external callback/exfiltration payloads or unrestricted load tests are needed.
- Record endpoint, actor/role, case, commit, expected/actual outcome and sanitized evidence. Assert against synthetic canary secrets rather than printing real tokens, cookies, codes or environment contents.
- A test-suite pass supports only its actual assertions. Where the matrix requires a new assertion or fixture, implement it in the isolated test suite or record the case as Not run/Blocked; a coverage pointer is not proof of completion.

## Recording and release decisions

Use the security rows in the [run record](test-run-template.md#security-case-results). Report Pass/Fail/Blocked/Not run per exact check and environment, attach evidence and state which assertions were exercised. If a case contains more than one boundary, record the sub-results instead of hiding a failure in an overall pass.

For SEC-04, record the confirmed prototype limitation against the authentication requirement as a known gap/Fail, even if a regression test correctly demonstrates the intended mock behavior. Keep that distinct from failures in the implemented Canvas staff controls. Keep deferred hosted controls visible; they are not Not applicable for a hosted release.

A security review must list unresolved findings, affected data/actions, severity, owner, remediation and retest evidence. Unauthorized staff access, cross-user access outside the documented mock identity limitation, forged payment acceptance, leaked integration secrets or execution in the portal origin block the relevant pilot gate. No production or comprehensive-security approval is implied by a functional test run, a dependency scan, or this document.
